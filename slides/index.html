Service commitments

Turn customer needs into measurable promises, costs, and consequences.

An example enterprise service level agreement

The work covered

One request = one report job:
one question + source documents → one report with citations.

Each job: up to 16,000 input tokens and 1,000 output tokens.

The application handles up to 20 report jobs at once, including queued jobs.

Example fee: US$20,000 per month.

The monthly commitments

95% of eligible requests return a complete report within 30 seconds.

99.9% of eligible requests succeed within the 60-second timeout.

If either target is missed, a 5% service credit means US$1,000 toward a future bill.

The measurement is the service level indicator (SLI), and its target is the service level objective (SLO).
The agreement and its consequences form the service level agreement (SLA).

Terminology: Google, Site Reliability Engineering, chapter 4. Terms and fee above are illustrative.

This simplified teaching example is not legal advice or an actual vendor SLA. Eligible means valid requests within the stated input, output and concurrency limits. Measure from receipt at the service boundary until the complete response is sent, including queueing, retrieval and inference; do not describe this as browser-observed latency. All eligible requests form the monthly denominator, including service rejections and failures. Failures count as latency misses. Success means a complete report response with citation fields and no service error within 60 seconds; it does not establish factual correctness. A result after 30 but within 60 seconds can pass the success target and miss the latency target. A single 5% credit applies if either or both targets are missed. Keep answer quality as a separate explicit release gate. A production contract would need fuller definitions and remedies. An internal SLO can be tighter than the contractual target; do not conflate them. Source for terminology, not numerical promises: https://sre.google/sre-book/service-level-objectives/ .

Engineering choices are proposed responses to the fictional SLA, not measured guarantees.

Start with a measured baseline. Break down the 30-second service budget before choosing an optimization. Test the stated workload envelope and realistic arrival patterns, not only 20 synchronized requests once. Long inputs and concurrent sequences affect cache memory and capacity. Larger batches can improve throughput but increase waiting time, so measure whether they help this latency objective. A single benchmark does not prove a monthly 99.9% service commitment. This is a teaching view of two overlapping layers, not an exclusive division of engineering jobs. Applied AI includes the full application flow, including how it calls the model and consumes its result. Inference engineering specializes in executing that model workload and serving it at the required quality, speed, reliability and cost. Input processing and generation are highlighted as the model execution stages. Hardware

How compute, memory, and bandwidth shape what a system can do.

What is a GPU?

A graphics processing unit is a processor built to do many similar calculations at the same time. That makes it useful for the matrix operations in AI models.

Compute is the calculation capacity: how much arithmetic the processor can perform per second.

A central processing unit (CPU) handles general program logic; a GPU accelerates large amounts of parallel arithmetic.

Kiely, Inference Engineering (2026), §§3.1–3.1.1, pp. 74–75.
Illustrative arithmetic, not a chip diagram or benchmark.

The book describes GPUs as performing a uniform operation over many independent data items and connects that ability to matrix multiplication in inference. Three lanes illustrate parallel work, not a literal GPU core count or timing claim. CPUs also support parallel and vector operations; this is a difference in specialization, not an absolute division. Modern GPUs include specialized matrix arithmetic units. Compute is often specified as floating-point operations per second, abbreviated FLOPS; compare the same number format and dense or sparse assumptions before comparing specifications. Do not equate more advertised compute with faster performance for every workload.

The 14 GB estimate excludes request state, workspace, and storage overhead.

One byte contains eight bits, so 16-bit weights use two bytes per value. Seven billion times two bytes is 14 billion bytes, or 14 decimal GB. This is an illustrative model size, not a named model specification. The book gives the related rule that a billion 8-bit parameters requires about one GB for weights. Request state includes cached attention values used during generation. Actual memory sizing also includes activations, workspaces, metadata and fragmentation. A particular workload may fail or slow down even if its weights fit. Apple silicon shares physical memory across the system, unlike the separate onboard memory on the datacenter GPUs discussed here, so do not treat installed Mac memory as wholly available to one model.

How the model processes an input and produces an answer.

Before answering, the model processes the question and source documents. It can work on many input tokens together.

Kiely, Inference Engineering (2026), §2.2, pp. 47–49; §2.4.2, pp. 63–66.
Prefill is often compute-limited; the actual workload and implementation determine the bottleneck.

Tokenization converts the question, instructions and documents into model input tokens before this phase. Prefill processes their representations through the trained model and builds the key-value cache, which holds attention state rather than a ready-made answer. Causal attention still restricts which positions can use other positions; processing input positions in parallel does not mean ignoring token order. The final prompt position supplies the distribution used to select the first output token, although engine accounting of that sampling step can vary. Weights are already resident on the accelerator in steady-state serving; do not confuse a forward pass with loading the model from disk. Prefix-cache hits can skip recomputation for reusable input. Larger uncached inputs create more work and state, but time does not scale by one universal formula.

Kiely, Inference Engineering (2026), §2.2, pp. 48–49; §2.4.2, pp. 63–66.
Batching and speculative decoding change how much useful work each execution step does.

For one ordinary autoregressive sequence, a newly chosen token becomes input to the next generation step, creating a sequential dependency. The model's learned weights remain unchanged. Cached attention state lets it avoid recomputing the entire earlier sequence, but reading that state still costs bandwidth. Repeated weight reads refer to accelerator memory traffic, not downloading or reloading the model from disk for each token. Batching shares execution across sequences and improves reuse; speculation can commit several verified output tokens per target-model pass. The claim about bandwidth applies especially to low-batch steady-state decode, not every model or hardware configuration.

This batches requests on one GPU; it does not mean combining GPUs. The same principle applies inside a multi-GPU serving group. Ordinary autoregressive decode produces one next token for each active sequence in a step; speculative decoding is a later exception. Model weights are shared, while attention state and outputs belong to each sequence. Batched matrix operations can reuse weight data and improve arithmetic intensity, increasing aggregate throughput. Reads are a conceptual simplification, not a claim that all weights are loaded in one physical transaction. Step time can rise with batch size; it need not rise in direct proportion, and small increases in batch size may barely change it. Separate waiting to form a batch from execution time. More context and more active sequences increase memory pressure. Measure throughput at the required per-request latency and quality; maximum throughput alone does not satisfy our 30-second report promise.

The book connects typical prefill to compute limits and typical low-to-moderate-batch decode to memory-bandwidth limits. These are not universal laws. Book example: many coding-assistant requests with large code contexts.

Prefill/decode disaggregation places the two phases in separate inference engines on separate GPUs or nodes. Both use the same model, but can use different parallelism, batching and resource allocations. Prefill computes the first output token and cached key/value attention state; that state is transferred over an interconnect to the decode worker, which produces subsequent tokens. Separating phases can reduce interference and let each pool scale independently, but transfer consumes time and bandwidth and two pools can be underutilized. Prefill queues and decode memory can become new bottlenecks. The book recommends this especially for high traffic, large models and long uncached inputs; its numerical rules of thumb are not universal thresholds. Conditional disaggregation can keep short or already-cached inputs on decode workers. Its coding-assistant example does not establish a particular company's deployment. For our report service, test the whole path under mixed arrivals: transfer and new queues must fit the existing 30-second budget. Do not assume twenty in-flight report jobs justify disaggregation or that gains will exceed overhead. This is distinct from splitting model layers across GPUs and from adding full-service replicas.
