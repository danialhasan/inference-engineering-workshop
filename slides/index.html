33–45 · Exercise 3 · Edit

Submit the jobs before waiting.

Edit exercises/ex03_concurrency.py.

from concurrent.futures import ThreadPoolExecutor

def schedule(jobs, workers):
    with ThreadPoolExecutor(max_workers=workers) as pool:
        futures = [pool.submit(job) for job in jobs]
        return [future.result() for future in futures]
python3 workshop.py check 3
python3 workshop.py run 3
Predict the group's finish time and each request's wait.
The starter calls job() one at a time and ignores workers. Submit every job first; collecting results later preserves input order without preventing overlap. future.result propagates failures. max_workers bounds concurrent jobs. Submitting and immediately waiting in the same loop would remain serial. The offline check verifies overlap, worker bound, output order and failure propagation. Recorded mode does not execute the attendee scheduler; --source live measures the edited implementation. Use down for the results and the server-capacity explanation.

Do not generalize the result to other server configurations. More client concurrency mostly moved waiting into the server queue. First-text time with one worker was roughly 7–8 ms after submission; some four-worker requests waited hundreds of milliseconds. The request timer excludes time waiting behind earlier jobs in the client. Compare group_ms for the full workload, and each request's end_ms for completion relative to group start. Group tokens/s divides all output tokens by elapsed group time; it is not per-user decoding speed. Recorded mode loads these groups without running the scheduler; check 3 verifies the edit and live mode measures it.

Exercise 3 · Explain the result

Client concurrency needs server capacity.

Your thread pool overlaps submissions.

The serving engine determines how requests share execution.

Measure group throughput and each user's wait.

Kiely, Inference Engineering (2026)
Ch. 7 §7.2.1, pp. 186–188; Fig. 7.8: Concurrency and Batch Sizing
Ch. 1 §1.4, pp. 35–37: Measuring Latency and Throughput
Printed pages; the examined PDF counter is two ahead. The book distinguishes static batching (wait for a full batch), dynamic batching (full batch or time cutoff), and continuous batching (admit requests as capacity becomes available). Figure 7.8 illustrates token-level continuous batching. A Python thread pool does not implement this or increase model-server capacity. Ask what server capacity to investigate next and whether the user's objective is an interactive response or batch completion. Chapter 1 distinguishes per-user token speed, total throughput, and end-to-end timing including queueing and networking. Attendees should state the objective and limits of their evidence in the worksheet.
